## 요청 줄 (버튼 20 · 자동화 9)

버튼이 눌리거나 자동화 조건이 맞으면 자동화 로그(학원) DB에 줄 하나를 만든다. 노션 웹훅은 같은 줄의 속성 변경을 약 60초 묶어 보내지만 새 줄 생성은 묶지 않아 몇 초 안에 도착한다.

| 칸 | 값 |
|-|-|
| 이름 | `<버튼/자동화 이름> 요청` |
| 발송 구분 | `버튼 요청` |
| 메모 | 동작 ID |
| 연결 칸 | 버튼은 "이 페이지", 자동화는 "트리거 페이지" |
| 발송자 | 버튼은 "클릭한 모든 사람", 자동화는 "트리거한 사람" |

- 버튼은 "이 페이지 편집"에서 `요청` 줄만 뺀다. 다른 단계(확인 표시 · 변수 · 웹훅 버튼 줄 등)는 그대로다.
- 자동화 9곳: 출석 `[웹훅] 보고서 전송`(`attendance-report-queue`) · `[웹훅] 수업 안내`(`attendance-lesson-notice-queue`), 보고서 `report-send`, 수강료 `tuition-notice`, 가정통신문 `letter-notice`, 청구서 `cart-notice`, 등록 `reg-textbook-queue` · `reg-timetable-notice`, 수업 `session-attendance-queue`. 트리거(`<이름> 상태` = ⚪ 대기)는 그대로다.
- 자동화 로그 쪽 연결 칸: 등록 · 학생 · 일정 · 수업 · 출석 · 보고서 · 수강료 · 가정통신문은 기존 칸, 클래스 · 메뉴 · 학습기록 · 진도관리 · 청구서 · 학교 · 시험정보는 새 한쪽 관계 칸(청구서는 기존 양쪽 `교재비` 대신 새 `청구서`).
- 자동화 로그와 양쪽 관계인 DB(학생 · 출석 · 보고서 · 청구서 · 수강료 · 가정통신문)의 `전송 내역` · `발송 횟수` 수식은 첫 관계에 `.filter(current.prop("발송 채널") == "알림톡")`를 붙여 요청 줄을 세지 않는다.
- 자동화 로그 보기: `전송 로그` = 발송 구분 ≠ 버튼 요청, `버튼 요청` = 발송 구분이 버튼 요청인 줄(성공 줄은 휴지통으로 가므로 남은 줄 = 실패 줄).

동작 ID와 함수는 예전과 같은 표(`supabase/functions/_shared/webhookRoutes.ts`, 46개)를 쓴다.

## 서버가 하는 일 (`_shared/notionRequests.ts` · `notionLogRequests.ts` · `notionEventsApply.ts`)

0. 요청 줄이면: 웹훅 구독이 자동화 로그 data source의 `page.created`를 알리면 서버가 그 줄을 읽는다. 발송 구분이 `버튼 요청`이면 메모의 동작 ID를 동작 표에서 찾고, 대상 줄을 연결 칸에서 찾는다(관계 칸 이름 = 동작 표 DB 이름에서 "(학원)"을 뺀 것, 없으면 값 있는 첫 관계). 대상 줄을 읽어 아래 2~4와 똑같이 처리한다. 결과는 대상 `요청` · `요청 결과`와 요청 줄 `발송 상태` · `발송일시` · `실패 사유`에 쓴다. 성공한 요청 줄은 바로 휴지통에 넣고(영구 삭제 아님, 노션 휴지통에서 되살림) 실패한 줄은 남긴다. 발송 구분이 `버튼 요청`이 아닌 줄(알림톡 기록 등)은 건드리지 않는다.
1. `요청` 칸 길: 웹훅 구독이 "이 줄이 바뀜"을 알린다 → 대기열(같은 줄은 2초 묶음) → 처리기가 그 줄을 다시 읽는다.
2. `요청`이 아는 동작 ID면 `요청` = `🔄 처리 중`, `요청 결과` = "🔄 처리 중 · 동작 이름 · 접수 시각".
3. 그 동작의 기존 함수로 넘긴다 — 길잡이와 같은 주소·같은 본문 모양(`{ data: 페이지 }`, 노션 자동화 웹훅과 같은 페이지 객체)·지금 서버 키. 함수의 잠금·상태·큐는 그대로다.
   - 요청 ID가 그 줄 `웹훅 정보` 수식에 들어 있으면 `웹훅 정보`의 ID를 모두 넘긴다(예전 자동화가 보내던 것과 같게).
4. 다시 읽어 `요청`이 아직 처리 중이면 `✅ 완료`(또는 `⚠️ 실패`), `요청 결과` = "✅ 완료 · 동작 이름 · 걸린 초 · 시각" / "⚠️ 실패 · 이유". 그 사이 새 요청이 들어왔으면 `요청`은 두고 `요청 결과`만 쓴다(새 요청은 대기열이 이어서 처리).
   - "완료" = 함수가 받았다는 뜻이다. 큐로 처리하는 함수(알림톡·보고서·수업 생성 등)의 실제 결과는 예전처럼 그 함수의 상태 칸(`보고서 전송 상태` 등)에 남는다.
   - 함수가 4xx로 답하면 실패 + 함수가 준 이유. 네트워크·5xx면 길잡이와 같은 "다시 넘기기"(sync_queue `notion-router-retry`, 최대 3번)에 넣고 그 사실을 적는다.
- **요청 줄은 묶이지 않는다**: 새 줄이라 같은 줄 2초 묶음 · 노션 약 60초 묶음이 없다.- **메아리**: 서버가 쓴 처리 중·완료·실패는 동작 ID가 아니라서 다시 읽어도 아무 일도 하지 않는다.
- **같은 줄 연속 누름**: 처리가 끝나 `요청`이 완료로 바뀐 뒤 다시 누르면 새 요청이다. 2초 안에 두 번 누르면 한 번으로 묶인다.
- **어느 DB를 읽나**: 사본이 없는 DB 이벤트는 원래 노션을 읽지 않는다. 데이터 소스마다 처음 한 번 읽어 `요청` 칸이 있는지 보고 표 `notion_request_sources`에 1시간 기억한다.
- `웹훅 버튼` 칸은 보지 않는다(옛 방식 버튼과 겹쳐 두 번 돌지 않게).

## 실패를 보는 곳과 `요청 결과` 글 (261123)

- **노션**: 메뉴관리 → 요청 실패(DB 20곳마다 `요청` = ⚠️ 실패인 줄만 보이는 표). 요청 줄 길은 자동화 로그의 `버튼 요청` 보기(남은 줄 = 실패 줄, `실패 사유`). 줄을 열어 `요청 결과`를 읽고 고친 뒤 버튼을 다시 누르면 새 요청이다.
- **관리 앱**: 홈 입력 점검 "노션 요청 실패"(누르면 목록 · [노션에서 열기]), 그 줄의 창 위 빨간 줄.
- **처리 중에 멈추지 않게**(v2.8.0 항목 114): 처리 중을 쓴 뒤 무엇이 실패해도 결과로 마무리한다. 함수가 통째로 죽어 남은 처리 중은 `status-watchdog`(5분마다)가 15분 넘게 고친 사람이 없는 줄을 `⚠️ 실패 · 처리 중에 서버가 끝을 알리지 못했어요(15분 넘음) …`로 바꾼다(찾는 DB = `notion_request_sources`에서 `요청` 칸이 있다고 기억한 DB).
- **자동 재시도 결과**(v2.8.0 항목 114): 넘기기 실패로 ⚠️ 실패가 된 요청을 다시 넘기기가 성공시키면 `요청` = ✅ 완료, `요청 결과` = `✅ 완료(자동 재시도) · 동작 이름 · 시각`. 함수가 거절하면 실패 그대로 이유만 바꿔 쓴다. 그사이 다시 눌렀으면 건드리지 않는다.
- `요청 결과` 꼴: `⚠️ 실패 · 동작 이름 — 무엇이 안 됐고 어떻게 하면 되는지 · 시각`. 내부 id · 함수 · 표 이름 · 영문 오류 원문은 칸에 쓰지 않고 함수 로그에만(`[notionRequests] … 실패 원문`).
  | 원문(함수가 준 이유) | 칸에 쓰는 말 |
  |-|-|
  | 리포트 캐시 줄 없음 | 학부모 리포트가 아직 만들어지지 않았어요. 반의 [학생 페이지 동기화]를 먼저 누른 뒤 다시 눌러 주세요 |
  | 네트워크 · 5xx(다시 넘김) | 서버가 잠깐 처리하지 못해 자동으로 다시 넘기고 있어요(최대 3번). 10분 뒤에도 실패면 다시 누르고, 계속되면 관리자에게 알려 주세요 |
  | 25초 넘김 | 서버가 25초 안에 답하지 않았어요. 몇 분 뒤 이 줄의 상태 칸을 보고, 그대로면 다시 눌러 주세요 |
  | 인증 실패 | 서버 연결 키가 맞지 않아요. 관리 앱 관리자 설정 → 연결에서 서버 상태를 확인해 주세요 |
  | 노션 한도 · 이미 처리 중 · 줄을 못 찾음 · 값 형식 | 각각 "1~2분 뒤 다시" · "결과를 보고 다시" · "지웠거나 공유 안 된 줄인지" · "비었거나 잘못 고른 칸" |
  | 그 밖의 한글 이유 | 이유에서 id · 영문 이름을 걷어낸 그대로(예: "보고서 구분이 비어 있습니다") |
  | 그 밖의 영문만 | 서버가 요청을 받지 않았어요(코드). 관리자에게 알려 주세요 |
- 바로 처리하는 함수(200으로 답함)가 줄의 `상태`를 ⚠️ 오류로 끝내면(예시 데이터가 모자랄 때 함수는 실패로 답하지 않고 `마지막 오류`에 이유를 씀) 요청도 ⚠️ 실패 + `마지막 오류`(예: "시험 기간 연결 — 학교와 시험을 먼저 고르세요."). 이번 요청 동안 생긴 오류만 본다(접수 전과 상태 · 마지막 오류가 다르거나 `처리 시작 시각`이 접수 뒤). 큐에 넣고 202로 답하는 함수(알림톡 · 보고서 · 수업 생성 등)는 결과가 나중이라 ✅ 완료(접수)로 두고, 실제 결과는 그 줄의 상태 칸에 남는다.
- 함수가 성공하면서 안내(`note`)를 주면 완료 뒤에 붙는다 — 예: 리포트를 아직 만든 적 없는 등록의 [링크 재발급]은 "✅ 완료 · 링크 재발급 · 1.2초 · 시각 · 학부모 리포트가 아직 없어 노션에 새 링크만 적었어요(반의 [학생 페이지 동기화]를 누르면 새 링크로 열려요)". (예전에는 이 경우를 오류로 던져 같은 실패를 3번 다시 넘겼다.)
- 구독이 끊긴 동안: 폴링이 그 줄을 찾으면 요청을 대기열에 넣어 처리한다(평소 몇 초 → 최대 5분). [notion-webhook-sync.md](notion-webhook-sync.md) "구독 끊김 알아채기".

## 관리 앱 단추 (261123, 항목 117)

관리 앱 실제 자료 모드의 단추도 노션 버튼과 **같은 줄 · 같은 칸**을 앱 저장 길(app-api `save` update)로 바꾼다 — 서버는 그 칸 변화를 노션 버튼과 똑같이 받는다(`prototype/admin-app/livereq.js`).
- `요청` = 동작 ID: 등록 `reg-link-regenerate` · `reg-registration-notice`, 진도관리 `progress-completion`, 학생 `student-inquiry`. 다른 화면은 공용 입구 `window.liveRequest(묶음, 줄들, 칸, 이름)`으로 같은 길을 쓴다(클래스 `class-etc-charge`는 재무 구조 정리 뒤).
- 자동화가 보는 상태 칸(노션 버튼도 이 칸만 바꿈): 등록 `교재 생성 상태` · `시간표 안내 상태` = ⚪ 대기(클래스 단추는 수강 중 등록마다). 노션 자동화는 앱(API)이 바꾼 칸에도 돈다(원본 실측).
- 학생 `개인정보 동의` 자동화(`student-inquiry-auto`)는 "동의 ☑인 새 줄"에서만 돈다 — 이미 있는 줄은 노션에서 체크해도 돌지 않았다(원본 실측 261123). 앱은 체크만 바꾸고 안내는 [접수 안내 전송]으로.
- 앱이 쓰지 못하는 것: 등록 [종료 처리](수업 DB까지 고침), 삭제 동작, 수강료 · 청구서 안내문 전송(서버 `APP_REQUEST_DENY`).

## 원본 상태

- 버튼 20 · 자동화 26, 46곳 모두 새 방식이다(웹훅 보내기 단계 0곳, 동작 ID가 서버 동작 표 46개와 1:1). 버튼 20 + 자동화 9곳은 요청 줄, 자동화 17곳은 `요청` 칸.
- **"아무 속성이 바뀌면" 도는 자동화는 `요청`을 쓰면 안 된다**: 서버가 `요청`·`요청 결과`를 쓰는 것도 속성 편집이라 자동화가 다시 돌아 약 1분마다 되풀이된다(원본 실측). 그래서 라이브러리 `[웹훅] 리포트 반영 · 속성 편집`은 트리거를 "아무 속성"에서 칸 14개(교재명 · ISBN13 · 가격 · 기타경비 항목 · 교육과정 · 구분 · 단원목록 · 사용중 · 출판사 · 시리즈 · 진도 단위 · 과목 · 전체 분량 · 교재 유형, "하나라도")로 좁혔다.
  - 파일 칸(`북커버` · `교재 PDF`)은 노션 트리거로 고를 수 없다 → 이 두 칸만 바꾼 경우 리포트 반영이 자동으로 돌지 않는다. 반의 [학생 페이지 동기화]를 누르면 반영된다.
  - 새 칸을 라이브러리에 더하면 트리거에도 더해야 자동 반영된다.

## 노션 칸 (DB마다 두 칸, 시스템 구역에 숨김)

- `요청` (select): 그 DB 동작 ID들 + `🔄 처리 중` · `✅ 완료` · `⚠️ 실패`
- `요청 결과` (텍스트)

## 되돌리는 법

- 버튼 하나: 요청 줄 만들기 단계를 지우고, 편집 단계에 `요청` = 동작 ID를 다시 넣는다(요청 칸 길). 웹훅 방식으로 되돌리려면 웹훅 보내기 단계를 넣는다(주소 `…/functions/v1/notion-router`, 헤더 `x-admin-key` = 웹훅 키, 보낼 속성 `웹훅 버튼`).
- 자동화 하나: "`요청` = ID" 단계(요청 줄 자동화 9곳은 요청 줄 만들기 단계)를 웹훅 보내기(같은 주소·키, 보낼 속성 `웹훅 정보` — 링크 2곳은 `웹훅 링크`, 수업 날짜 이동은 `웹훅 수업일시`)로 바꾼다.
- 서버 전체: 함수 설정 `NOTION_EVENTS_REQUESTS=off` → 요청을 넘기지 않는다(사본 반영은 그대로). 이때는 버튼을 옛 방식으로 되돌려야 동작한다.
- 요청 줄만: `NOTION_EVENTS_LOG_REQUESTS=off` → 요청 줄을 처리하지 않는다(`요청` 칸 길은 그대로). 성공 줄을 휴지통에 넣지 않기만: `NOTION_LOG_REQUEST_TRASH=off`.
