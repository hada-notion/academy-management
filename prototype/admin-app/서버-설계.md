# 관리 앱 서버 연결 설계

> 관리 앱이 예시 데이터 대신 실제 노션 자료로 돌아가게 하는 설계. 아직 만들지 않았다(설계만). 근거: `구조-파악.md`(서버 함수 41개·테이블), `기능-대응표.md`.

## 1. 원칙
| 원칙 | 내용 |
|-|-|
| 원본은 노션 | 앱은 노션을 직접 바꾸는 창구. Supabase에는 빨리 보여 주기 위한 복사본만 둔다 |
| 읽기 = 복사본 | 화면은 Supabase 복사본을 읽는다(노션 API는 느리고 초당 3건 제한) |
| 쓰기 = 노션 먼저 | [저장] → 서버 함수가 노션에 쓰고, 그 응답을 복사본에 바로 반영(지금 `class-room`과 같은 방식) |
| 있는 것을 쓴다 | 수업·출결·보강·학습기록 = `class-room`, 교재 = `textbook-api`, 학교 = `school-api`, 서류 = `get-legal-document-data`, 로그인 = `admin-security` |
| 노션 자동화는 그대로 | 앱이 쓴 값으로 노션 자동화·버튼이 평소처럼 돈다(알림톡·수업 생성 등). 앱이 같은 일을 두 번 하지 않는다 |

## 2. 새로 필요한 것
### 2-1. 복사본 테이블(읽기용)
| 테이블 | 노션 DB | 쓰는 화면 |
|-|-|-|
| app_students | 학생 | 학생 · 고르기 목록 |
| app_enrolls | 등록 | 수강 · 학생 창 등록 카드 |
| app_classes | 클래스 | 클래스 · 시간표 |
| app_timetables | 시간표 | 시간표 |
| app_teachers | 강사 | 선생님 |
| app_subjects · app_progress | 과목 · 진도교재 | 과목 · 진도교재 |
| app_events | 일정 | 일정 |
| app_tuition · app_bookfees · app_payments | 수강료 · 교재비 · 결제 | 수강료 · 교재비 · 비용 |
| app_outbox · app_reports · app_letters | 알림톡 발송함 · 보고서 · 가정통신문 | 학습 보고서 · 가정통신문 |
| app_schools · app_exams · app_scores | 학교 · 시험정보 · 성적 | 학교 · 시험 |
| app_alims · app_autolog | 알림톡 설정 · 자동화 로그 | 알림톡 설정 |
- 수업·출석·학습기록·학습활동은 이미 있는 `cr_*`, 교재·단원은 `lib_*`를 그대로 쓴다.
- 모든 줄에 노션 페이지 ID·마지막 고친 시각을 둔다(→ 화면의 [노션] 가기, 충돌 확인).
- 동기화: 증분 5분마다 + 밤에 전체 대조(`sync-class-room-copy`와 같은 틀을 넓힘).

### 2-2. 서버 함수 `app-api`(관리자 세션으로 부름)
| 동작 | 하는 일 | 노션에서 일어나는 일 |
|-|-|-|
| list(collection, since) | 복사본 읽기(바뀐 것만) | — |
| save(changes[]) | 작성 중인 것을 한 번에: 만들기·고치기·삭제 예정 처리. 노션에 순서대로 쓰고(초당 3건) 결과를 복사본에 반영, 실패한 줄은 이유와 함께 돌려줌 | 페이지 만들기·속성 고치기·휴지통 |
| conflict(ids) | 저장 전에 노션에서 그사이 바뀐 줄 확인 | — |
| run(action, id) | 노션 버튼이 하던 일을 앱에서: 수업 일괄 생성 · 출석 조정 · 종료 처리 · 교재 생성 · 수료 · 보고서 생성 · 월 수강료 생성 · 가정통신문 생성 · 안내 전송 | 상태 속성을 "대기"로 → 기존 자동화·큐가 처리 |
- `run`은 새 로직을 만들지 않는다. 노션 버튼과 똑같이 상태 속성만 바꿔 기존 흐름을 탄다.
- 보안: `SECURITY_BROWSER_ROUTES`에 `app-api`를 넣는다. 웹훅 키로만 부르던 함수는 앱이 직접 부르지 않는다.

### 2-3. 앱 쪽
| 항목 | 내용 |
|-|-|
| 자료 층 | 지금 시제품의 `DB`(예시 데이터)를 `list` 결과로 바꿔 끼움. 화면 코드는 그대로 |
| 저장 | 위 [저장 n]의 목록을 `save`로 보냄. 줄마다 성공·실패를 저장 창에 표시, 실패한 줄은 작성 중으로 남김 |
| 로그인 | 기존 `admin_auth.js` 세션(12시간) |
| 주소 | `hada_config.js`(학원별 Supabase 주소·공개 키) 그대로 |

## 3. 순서(작게 나눠 배포하고 검증)
| 단계 | 내용 | 검증 |
|-|-|-|
| 1 | 읽기 전용: 복사본 테이블 + 동기화 + `app-api list` + 앱 자료 층 | 원본 노션 건수와 복사본 건수 대조, 화면 값 표본 대조 |
| 2 | 수업 쪽 쓰기: 출결·보강·학습기록을 `class-room`으로(기존 수업 관리 화면 대체) | 기존 화면과 같은 값이 노션에 들어가는지 |
| 3 | 기준 정보 쓰기: 선생님·과목·학교·일정·비용(이어진 자동화가 적은 것부터) | 노션 값·자동화 로그 |
| 4 | 학생·등록·클래스·시간표 쓰기 + `run`(수업 생성·종료 처리) | 예시 데이터 학원에서 한 주 운영 흉내 |
| 5 | 청구·발송: 수강료·교재비·보고서·가정통신문 `run` | 알림톡은 꺼 둔 채 발송함 상태만 확인 |
| 6 | 기존 화면 정리: 관리자 설정·수업 관리·라이브러리·학교 찾기·법정 서류를 앱으로 옮긴 뒤 옛 HTML 삭제 | 옛 주소로 오면 앱으로 보냄 |
- 단계마다 PR 하나, CHANGELOG·`docs/updates` 한 항목. `main` 병합 = 모든 학원 공개이므로 대표 승인 뒤.

## 4. 대표 결정이 필요한 것
- 매뉴얼과 시제품이 다르게 동작하는 12곳(`기능-대응표.md` 6장) — 서버 규칙은 매뉴얼(노션 자동화)이 기준이므로, 앱을 매뉴얼에 맞출지 매뉴얼·자동화를 고칠지.
- 시즌: 노션에 없는 개념. 앱 안에서만 쓰는 "보는 기간"으로 둘지(추천), 노션에 DB를 만들지.
- 학부모 리포트·키오스크: 링크로만 잇고 따로 유지(추천).
